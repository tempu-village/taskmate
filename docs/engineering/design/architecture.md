# Architecture

Status: Current implementation map.

## Components

[main.ts](../../../src/main.ts) owns plugin startup, settings, commands and Vault event subscriptions. It constructs Task/Project repositories and refreshes views when managed files change. [settings.ts](../../../src/settings.ts) owns plugin settings; source indexing and machine-local Vault registration are not implemented.

Source files are grouped by product capability rather than by layer; a folder may hold Domain, Persistence Adapter and UI Adapter files together. `src/tasks/` holds Task types, Markdown representation, edit merging, date suggestions, the Task repository, and failure collection for writes across several Tasks. `src/projects/` holds Project Markdown, persistence and the Project modal. `src/labels/` holds Label normalization and recent-label suggestions, management and picker models, Label rename and removal across Tasks, and their modals; editors pass Label data to the picker through its `LabelEditingOptions`. `src/task-editor/` holds the Task, Step and conflict modals and the Task editing flow that opens them, saves edits, resolves conflicts and deletes from the editor. `src/task-list/` holds the TaskMate ItemView, list model and renderer, filters, multi-selection state, scroll preservation and bulk editing. `src/shared/` holds the mobile keyboard layout used by both editors and bulk editing, and the SHA-256 helper used by both review kinds. `src/i18n/` owns translation catalogs, and `src/reviews/` is described below. Folder dependencies run `task-list → task-editor → labels / projects → tasks`, with `reviews → tasks`; a folder may skip levels, `tasks` imports no other feature folder, and any folder may use `i18n` or `shared`. The `task-list`, `reviews` and `settings.ts` references to `main.ts` are type-only. The [Module boundary test](../../../test/module-boundaries.test.ts) enforces these folder rules. Tests mirror these folders under `test/`.

[view.ts](../../../src/task-list/view.ts) is the Obsidian ItemView adapter. It loads domain data, owns navigation state, opens modals and dispatches persistence actions. Creating and editing a Task is delegated to [task-editing-flow.ts](../../../src/task-editor/task-editing-flow.ts), which receives the repositories, Label options, recent-Label recording and a refresh callback from the view. Writes that span several Tasks are delegated: [label-maintenance.ts](../../../src/labels/label-maintenance.ts) renames or removes a Label across Tasks and returns updated Label preferences, and [bulk-task-actions.ts](../../../src/task-list/bulk-task-actions.ts) applies bulk edits; both return the Tasks whose write failed, while the view keeps notices, settings persistence and selection updates. [task-filter-state.ts](../../../src/task-list/task-filter-state.ts) and [task-selection.ts](../../../src/task-list/task-selection.ts) hold the filter criteria and the multi-selection scope and selection that the view reads and updates. [task-list-model.ts](../../../src/task-list/task-list-model.ts) builds pure display sections; [task-list-renderer.ts](../../../src/task-list/task-list-renderer.ts) renders DOM and owns listeners/Sortable cleanup. Rendering emits intent; repository writes remain in the adapter/repositories.

[domain.ts](../../../src/tasks/domain.ts) owns Task/Project types and pure filtering, grouping and sorting. [repository.ts](../../../src/tasks/repository.ts) and [project-repository.ts](../../../src/projects/project-repository.ts) use public Obsidian APIs; [markdown.ts](../../../src/tasks/markdown.ts), [task-body.ts](../../../src/tasks/task-body.ts) and [project-markdown.ts](../../../src/projects/project-markdown.ts) handle portable representation.

`src/reviews/task-change/` is the Task change review feature Module. [proposal.ts](../../../src/reviews/task-change/proposal.ts) is its pure Domain implementation: it validates evidence, derives TaskMate-owned jsdiff hunks, checks exact patch replay and calculates approved writes and follow-up Proposals. Its stale guard compares complete Markdown, so a concurrent `rank` update from Manual order is preserved by returning a regenerated follow-up rather than merging a write against the old snapshot. [proposal-repository.ts](../../../src/reviews/task-change/proposal-repository.ts) is the Persistence Adapter for pending/history Vault storage and stale-checked writes. [review-renderer.ts](../../../src/reviews/task-change/review-renderer.ts) owns DOM rendering and emits review intent without persistence; [review-scroll.ts](../../../src/reviews/task-change/review-scroll.ts) preserves list position; [review-view.ts](../../../src/reviews/task-change/review-view.ts) is the Obsidian UI Adapter and coordinates the concrete repository, renderer and ItemView lifecycle on desktop and mobile. The protocol handler in `main.ts` accepts stable identifiers and can reveal a review but cannot approve or write.

The dependency direction is `main.ts → review-view.ts → proposal-repository.ts / review-renderer.ts / review-scroll.ts`, with the repository and renderer depending on `proposal.ts`. The pure Proposal Domain depends on the existing Task/Markdown Domain but not on Obsidian, DOM, or Vault. The type-only `review-view.ts → main.ts` reference is erased at runtime. The Source candidate review is a sibling that shares review CSS classes and the jsdiff library with it, and it was added without changing the Task change Proposal Domain. [Module boundaries](module-boundaries.md) owns the dependency and Interface rules that this map applies.

`src/reviews/shared/` holds the Review Catalog, the one contract both review kinds use with the same meaning ([#62](https://github.com/tempu-village/taskmate/issues/62)). [review-catalog.ts](../../../src/reviews/shared/review-catalog.ts) reads only the envelope of each JSON file directly inside the Proposal folder or its History folder and classifies it: `source-review-*` with `reviewType: source-candidate` as a Source candidate review, `proposal-*` without a `reviewType` as a version 1 Task change Proposal, and anything else, including mismatched IDs and unsupported versions, as an unreadable file. It never parses a complete payload or writes. [review-index.ts](../../../src/reviews/shared/review-index.ts) joins those entries with each owning Module's list details, so a file its Module cannot read is shown as unreadable rather than hidden or opened, and renders the shared Pending/History list. [review-index-view.ts](../../../src/reviews/shared/review-index-view.ts) is its Obsidian UI Adapter. `main.ts` routes an entry to the owning review view in the same leaf, and each review view's back action returns there, so neither review kind imports the other and shared code imports neither. The `Open reviews` command opens the list; the two review URIs still open a review directly.

`src/reviews/source-candidate/` is the Source candidate review feature Module ([#61](https://github.com/tempu-village/taskmate/issues/61)). [proposal.ts](../../../src/reviews/source-candidate/proposal.ts) is its pure Domain: it validates the versioned Source candidate Proposal against the [Source candidate Proposal format](../specifications/source-candidate-proposal-format.md), verifies merge evidence, and calculates candidate edits, decisions, application results, review status and health, formal-apply eligibility, and Source-note completion. [review-repository.ts](../../../src/reviews/source-candidate/review-repository.ts) is its Persistence Adapter: it lists, loads and saves `source-review-*.json` under the Proposal folder and History, and performs formal apply. Formal apply rechecks every referenced Source, applies eligible candidates in ID order, saves the review after each one, and stops if a save fails. Created Tasks use an ID derived from the review, candidate and revision, and a merge whose target already equals its after-Markdown counts as applied, so a retry after an interrupted apply neither duplicates nor re-merges. It then writes provenance on completed notes and archives a fully applied review. [source-note-provenance.ts](../../../src/reviews/source-candidate/source-note-provenance.ts) reproduces Task Pilot's Source-note hash, including its newline handling, and its provenance lines. Provenance is retried on every formal apply until written, and is skipped and reported when a note changed after staging. [review-renderer.ts](../../../src/reviews/source-candidate/review-renderer.ts) owns DOM rendering and emits review intent without persistence. It renders one card per candidate, with its Sources as quotes, then the Task draft, the merge summary with an inline diff, or the exclusion reason, and decision and Edit buttons. Edit replaces the card body with a form for the allowed fields, where the operation can switch between create, exclude and, when Task Pilot staged merge evidence, merge. It also renders the formal-apply confirmation, which lists blocked candidates and requires an explicit acknowledgement for unviewed merges. [review-view.ts](../../../src/reviews/source-candidate/review-view.ts) is the Obsidian UI Adapter: it saves decisions, viewed diffs and edits, runs formal apply only from that confirmation, and reports the result. [candidate-edit-form.ts](../../../src/reviews/source-candidate/candidate-edit-form.ts) converts a candidate to form values and back, reports field errors, and refuses a save when the candidate changed after editing began; the Domain then increments the revision, returns the candidate to pending and regenerates merge evidence. The shared review list and the `obsidian://taskmate-source-review` URI open it; the URI accepts only a review ID and cannot decide, edit or apply. The Task change repository lists only `proposal-*.json`, so Source candidate reviews never appear as malformed Task change Proposals.

Task Pilot, the [portable agent skill](../../../skills/taskpilot/SKILL.md), runs separately in an agent host. Its Python helpers operate on the same Markdown contract; they are not bundled plugin runtime dependencies. `scripts/source_review.py` stages Source candidate Proposal JSON for the Source candidate review; a [contract test](../../../test/reviews/source-candidate/staging-contract.test.ts) runs it and checks the output with TaskMate's Domain validator and the Draft 2020-12 Schema.

## Change boundaries

Use browser/public Obsidian APIs in plugin runtime; Node/Python belong to build and external tooling. Preserve renderer teardown on rerender/close. Update both Markdown writers when changing a format, using [data ownership](data-model.md). Consult [source import](../features/source-import.md) or [edit conflicts](../features/edit-conflicts.md) when changing those flows.

## Evidence

[Model tests](../../../test/task-list/task-list-model.test.ts), [renderer tests](../../../test/task-list/task-list-renderer.test.ts) and [mobile layout tests](../../../test/mobile-layout.test.ts) cover selected boundaries. [Module boundary tests](../../../test/module-boundaries.test.ts) cover runtime import cycles and the folder dependency rules. Device verification remains separate.

[Proposal tests](../../../test/reviews/task-change/proposal.test.ts), [Proposal repository tests](../../../test/reviews/task-change/proposal-repository.test.ts), [review renderer tests](../../../test/reviews/task-change/review-renderer.test.ts), and [review Module boundary tests](../../../test/reviews/review-module-boundaries.test.ts) cover deterministic evidence, partial approval, isolated stale/write failures, history/follow-up persistence, DOM intent, and forbidden dependencies between review Modules. Task Pilot tests cover macOS, Windows, and Linux URI dispatch without invoking a shell. [Source candidate Domain tests](../../../test/reviews/source-candidate/proposal.test.ts) and [Schema tests](../../../test/reviews/source-candidate/schema.test.ts) check the Specification's example, validation, transitions and Source-note completion, and validate every written state against the Draft 2020-12 Schema with the development-only `ajv` package. [Formal-apply tests](../../../test/reviews/source-candidate/review-repository.test.ts) cover acknowledgement, stale Sources and merge targets, interrupted applies, failures, save failures and provenance retry, and [provenance parity tests](../../../test/reviews/source-candidate/source-note-provenance.test.ts) compare hashes and written lines with Task Pilot. [Source candidate renderer tests](../../../test/reviews/source-candidate/review-renderer.test.ts) cover cards, decision state, inline diffs, the acknowledgement gate and the edit form, and [edit form tests](../../../test/reviews/source-candidate/candidate-edit-form.test.ts) cover conversion, field errors, operation switches and save conflicts. The macOS direct-URI spike is manual evidence; fresh Windows/Linux URI delivery and mobile visual verification remain gaps.

mainは起動、設定、コマンド、Vaultイベントを管理し、viewは画面状態、データ取得、操作と保存を調整し、絞り込み条件と複数選択の状態はそれぞれtask-filter-stateとtask-selectionが持ちます。Taskの作成と編集はtask-editing-flowへ任せ、repository、Labelの選択肢、最近使ったLabelの記録、再描画の呼び出しをviewから渡します。複数Taskへの書き込みは、Labelの改名・削除をlabel-maintenance、一括編集をbulk-task-actionsへ任せ、どちらも書き込みに失敗したTaskを返します。通知、設定の保存、選択の更新はviewに残します。task-list-modelは表示モデル、task-list-rendererはDOMとSortableの後片付けを担います。domainは型と純粋な絞り込み・並べ替え、repositoryは公開Obsidian APIを使った保存、Markdown関連モジュールは表現を扱います。

Task変更Reviewは`src/reviews/task-change/`へ集約します。`proposal.ts`は純粋Domain、`proposal-repository.ts`はVault Persistence Adapter、`review-renderer.ts`と`review-scroll.ts`はDOM表示と位置保持、`review-view.ts`はObsidian UI Adapterです。依存はUIとPersistence AdapterからDomainへ向け、DomainからObsidian、DOM、Vaultへは向けません。Source候補Reviewは兄弟Moduleで、Task変更ReviewとはReview用のCSS classとjsdiffライブラリを共有します。依存方向とInterfaceの規則は[module boundaries](module-boundaries.md)を正本とします。

`src/reviews/shared/`には、両方のReviewが同じ意味で使う唯一の契約であるReview Catalogを置きます（#62）。`review-catalog.ts`は、Proposalフォルダーとその履歴フォルダーの直下にあるJSONの「封筒」だけを読んで分類します。`reviewType: source-candidate`を持つ`source-review-*`はSource候補レビュー、`reviewType`のない`proposal-*`は版1のTask変更Proposal、それ以外（IDの不一致や対応していない版を含む）は読めないファイルです。中身全体の解析や書き込みはしません。`review-index.ts`は、その分類と各Review Moduleの一覧情報を合わせ、Moduleが読めないファイルを隠したり開いたりせず「読めないファイル」として示し、未レビューと履歴の共通一覧を描きます。`review-index-view.ts`はそのObsidian UI Adapterです。どのReview画面で開くかは`main.ts`が決めて同じタブで開き、各Review画面の戻るボタンはこの一覧へ戻るため、Review種別どうしもsharedも互いをimportしません。「レビューを開く」コマンドで一覧を開き、2つのレビューURIはこれまでどおりレビューを直接開きます。

Source候補Reviewは`src/reviews/source-candidate/`の機能Moduleです（#61）。純粋Domainの`proposal.ts`は、[Source candidate Proposal format](../specifications/source-candidate-proposal-format.md)に沿ってSource候補Proposalを検証し、統合の根拠を確かめ、候補の編集、判断、反映結果、レビューの状態と健全性、正式反映の対象、Source noteの完了を計算します。`review-repository.ts`はPersistence Adapterで、Proposalフォルダーと履歴の`source-review-*.json`の一覧・読み込み・保存と正式反映を担います。正式反映では参照するSourceを確かめ直し、反映できる候補をID順に1件ずつ反映して毎回保存し、保存に失敗したらそこで止まります。作るTaskのIDはレビュー・候補・版番号から決まり、変更後のMarkdownと既に一致する統合先は反映済みとみなすため、中断後にやり直しても二重に作ったり統合したりしません。その後、完了したノートへ取り込み履歴を書き、全候補を反映したレビューをHistoryへ移します。`source-note-provenance.ts`は、改行の扱いを含めてTask PilotのSource noteハッシュと取り込み履歴の行を再現します。取り込み履歴は書けるまで正式反映のたびにやり直し、ステージ後にノートが変わっていれば書かずに報告します。`review-renderer.ts`はDOM表示を担い、保存はせずにレビューの操作を伝えます。候補ごとに1枚のカードを作り、Sourceを引用で示し、Taskの下書き、差分を開ける統合の要約、または除外理由と、判断ボタンを表示します。判断ボタンの横の編集ボタンを押すと、カード本文が許可された項目の入力欄に替わります。操作は作成と除外、Task Pilotが統合の根拠を用意した候補では統合にも切り替えられます。正式反映の確認画面も描き、今は反映されない候補を示し、差分を見ていない統合があれば明示的な確認を求めます。`review-view.ts`はObsidian UI Adapterで、判断、差分を見たこと、編集を保存し、確認画面からだけ正式反映を実行して結果を知らせます。`candidate-edit-form.ts`は候補と入力欄の値を相互に変換し、項目ごとの入力エラーを返し、編集を始めた後に候補が変わっていれば保存を断ります。その後Domainが版番号を上げ、候補を未決に戻し、統合の根拠を作り直します。共通のレビュー一覧と`obsidian://taskmate-source-review` URIで開きます。URIはレビューIDだけを受け取り、判断も編集も反映もできません。Task変更のrepositoryは`proposal-*.json`だけを一覧にするため、Source候補レビューが壊れたTask変更Proposalとして扱われることはありません。

Task PilotとPython helperは別のホストで同じMarkdown契約を操作します。`scripts/source_review.py`はSource候補ReviewのためのSource候補Proposal JSONを作り、契約テストがその出力をTaskMateのDomainの検証とDraft 2020-12の型定義で確かめます。Proposalのstale判定はMarkdown全体を比較するため、Manual orderによる`rank`の並行更新も古い書き込みと混ぜず、現在の内容を基準にしたfollow-upへ戻します。プラグイン実行時へNode/Pythonを持ち込まず、描画の破棄処理を保ち、形式変更時は双方のwriterを更新します。型・モデル・DOMテストと実機検証の範囲は[testing](testing.md)で区別します。
